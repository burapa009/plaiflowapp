ลงมือแก้ไขระบบแบบฟอร์มเอกสารทางบัญชีของ PlaiFlow ใน repository จริง โดยใช้ข้อกำหนดในไฟล์แนบเป็นพื้นฐาน และใช้คำสั่งนี้กำหนดรายละเอียดฟอร์มแต่ละประเภทเพิ่มเติม

งานนี้ต้องแก้หน้าจอที่ผู้ใช้เปิดใช้งานจริง ไม่ใช่เพียงเพิ่ม document types, configuration, schema หรือเขียนแผนงานแล้วจบ

เป้าหมาย:
1. เอกสารแต่ละประเภทมีฟอร์มที่เหมาะกับข้อมูลและหน้าที่ของเอกสารนั้น
2. เปลี่ยนประเภทแล้วหัวข้อ ช่องกรอก ตาราง และ validation เปลี่ยนจริง
3. ข้อมูลเชื่อมกับ API และบันทึกลงฐานข้อมูลจริง
4. เอกสารที่ระบบออกได้มีแบบพิมพ์ที่ใช้ข้อมูลชุดเดียวกับฟอร์ม
5. ผู้ใช้ตรวจ OCR แก้ข้อมูล บันทึกร่าง และยืนยันได้ตามสิทธิ์เดิม

## 1. ตรวจให้พบฟอร์มที่ใช้งานจริงก่อนแก้

อ่าน AGENTS.md และติดตามเส้นทางตั้งแต่:
- รายการเอกสาร → เปิดรายละเอียด → แก้ไข → บันทึก
- OCR upload → ประมวลผล → เปิดฟอร์มตรวจสอบ
- สร้างเอกสารใหม่ → เลือกประเภท → กรอก → บันทึก → พิมพ์

ตรวจ route, component ที่ render จริง, form state, API payload, database และ print renderer

หากมีฟอร์มหลายเวอร์ชัน ให้ตรวจว่า route ปัจจุบันใช้ตัวไหน ห้ามแก้ component ที่ไม่ได้ถูกเรียกใช้แล้วรายงานว่าเสร็จ

หากฟอร์มถูกควบคุมด้วย feature flag หรือเงื่อนไขอื่น ให้ตรวจและเชื่อมการใช้งานให้ถูกต้อง

สรุปสั้น ๆ ว่าฟอร์มปัจจุบันอยู่ที่ไหนและจะแก้ไฟล์ใด จากนั้นลงมือทำต่อทันที

## 2. แยกงานเป็นสองส่วนที่เชื่อมกัน

A. ฟอร์มข้อมูลเอกสาร
ใช้สร้าง ตรวจสอบ และแก้ไขข้อมูลเอกสาร รวมถึงข้อมูลจาก OCR

B. แบบเอกสารสำหรับพิมพ์ / PDF
ใช้กับเอกสารที่ PlaiFlow รองรับการออกเอกสารจริง

ทั้งสองส่วนต้องใช้ canonical document data เดียวกัน ห้ามสร้าง state หรือข้อมูลจำลองแยกกันจนยอดและชื่อคู่ค้าไม่ตรงกัน

เอกสารที่นำเข้าจากภายนอกต้องเก็บต้นฉบับไว้ การแสดงข้อมูลใหม่ไม่ถือเป็นการออกเอกสารแทนผู้ออกเดิม

หากยังไม่มีระบบออกเอกสารบางประเภท ให้ทำฟอร์มข้อมูลให้ครบ และระบุความสามารถในการออกเอกสารตามจริง ห้ามแสดงว่าออกเอกสารทางการสำเร็จจากเพียงหน้าพรีวิว

## 3. โครงสร้างฟอร์มร่วม

ใช้ shared components และ type configuration ตาม architecture เดิม เช่น:
- DocumentHeaderFields
- PartyFields
- LineItemsEditor
- AmountSummary
- PaymentFields
- ReferenceDocuments
- AttachmentFields
- SignatureSection

ชื่อ component ปรับให้เข้ากับโปรเจกต์ได้ ไม่ต้องยึดชื่อตัวอย่าง

แต่ละประเภทต้องกำหนด:
- ชื่อเอกสาร
- sections และลำดับที่แสดง
- บทบาทของแต่ละฝ่าย
- fields ที่ใช้จริง
- required fields สำหรับร่างและยืนยัน
- กติกาคำนวณและ validation
- ความสัมพันธ์กับเอกสารอื่น
- ความสามารถในการออกและพิมพ์เอกสาร

ห้ามใช้ฟอร์มใบเสร็จชุดเดียวกับทุกประเภทแล้วเปลี่ยนเฉพาะชื่อหัวข้อ

## 4. แบบฟอร์มแต่ละประเภท

### 4.1 ใบเสร็จรับเงิน
แสดง:
- เลขที่เอกสารและวันที่รับเงิน
- ผู้รับเงิน/ผู้ออกเอกสาร
- ผู้จ่ายเงิน
- รายการที่รับชำระ และเอกสารอ้างอิง
- ยอดรวมเอกสาร
- ยอดรับชำระครั้งนี้
- วิธีรับชำระ วันที่ และเลขอ้างอิงการชำระ
- ยอดคงเหลือเมื่อเชื่อมกับรายการต้นทาง
- หมายเหตุและผู้รับเงิน

อย่าสรุปว่าชำระครบจากชื่อเอกสารเพียงอย่างเดียว

### 4.2 ใบกำกับภาษีเต็มรูป
แสดง:
- เลขที่เอกสารและวันที่
- ข้อมูลผู้ออกและผู้รับเอกสาร: ชื่อ ที่อยู่ เลขภาษี และสาขา
- ตารางสินค้า/บริการ: รายละเอียด จำนวน หน่วย ราคาต่อหน่วย ส่วนลด และจำนวนเงิน
- ฐานภาษี อัตราภาษี ยอด VAT และยอดรวม
- โหมดราคารวม/ไม่รวม VAT
- เอกสารอ้างอิงและหมายเหตุ

ใช้กฎตรวจสอบที่มีที่มาในระบบ ห้ามถือว่าฟอร์มกรอกครบแปลว่าใช้เครดิตภาษีได้

### 4.3 ใบเสร็จรับเงิน/ใบกำกับภาษี
รวมข้อมูลใบกำกับภาษีและการรับชำระไว้ในเอกสารเดียว:
- ข้อมูลคู่ค้าและรายการสินค้า
- ฐานภาษี VAT และยอดรวม
- ยอดรับชำระ วิธีชำระ วันที่ และเลขอ้างอิง
- ผู้รับเงินและหมายเหตุ

ไม่สร้างรายการบัญชีสองรายการเพียงเพราะเอกสารมีสองหน้าที่

### 4.4 ใบแจ้งหนี้
แสดง:
- เลขที่เอกสาร วันที่ออก และวันครบกำหนด
- ผู้เรียกเก็บและผู้ถูกเรียกเก็บ
- เงื่อนไขเครดิต
- เลขอ้างอิงใบสั่งซื้อ/สัญญา ถ้ามี
- ตารางสินค้า/บริการ
- ส่วนลด ฐานภาษี VAT และยอดรวม
- ข้อมูลการชำระเงินของผู้ออก หากมีจริง
- เอกสารรับชำระที่เชื่อมโยงและยอดคงเหลือ

ไม่แสดงว่าชำระแล้วโดยอัตโนมัติ

### 4.5 ใบวางบิล
แสดง:
- เลขที่ วันที่วางบิล และกำหนดชำระ
- ผู้วางบิลและผู้รับวางบิล
- ตารางเลือกใบแจ้งหนี้หลายใบ
- แต่ละแถวมีเลขที่ วันที่ ยอดเอกสาร ยอดชำระแล้ว และยอดที่นำมาวางบิล
- ยอดรวมที่เรียกเก็บในครั้งนี้
- ผู้ส่งและผู้รับวางบิล หาก workflow รองรับ

ตรวจเอกสารอ้างอิงให้อยู่ใน organization เดียวกันและมีคู่ค้า/สกุลเงินที่เข้ากันได้

### 4.6 ใบส่งของ
แสดง:
- เลขที่เอกสาร วันที่ส่ง และเอกสารอ้างอิง
- ผู้ส่งและผู้รับสินค้า
- ที่อยู่จัดส่งแยกจากที่อยู่คู่ค้า
- ตารางสินค้า จำนวน หน่วย และจำนวนส่งจริง
- ผู้ส่ง ผู้รับ และวันที่รับ
- หมายเหตุการส่ง

ราคาและภาษีแสดงเฉพาะรูปแบบที่ใช้จริง ไม่บังคับยอดเงินกับใบส่งของที่มีเพียงจำนวนสินค้า

### 4.7 ใบสำคัญรับเงิน
แสดง:
- เลขที่และวันที่
- ธุรกิจหรือผู้จ่ายเงิน
- ผู้รับเงินและข้อมูลระบุตัวตนตามที่ระบบจำเป็นต้องใช้
- รายละเอียดและเหตุผลการจ่าย
- ยอดเงินก่อนหัก ภาษีหัก ณ ที่จ่ายถ้ามี และยอดรับสุทธิ
- วิธีชำระและเอกสารอ้างอิง
- ผู้รับเงิน ผู้จ่ายเงิน และผู้อนุมัติตาม workflow

แบบพิมพ์มีพื้นที่ลงนามที่เหมาะสม แต่ห้ามสร้างลายเซ็นหรือสถานะลงนามปลอม

### 4.8 ใบแทนใบเสร็จรับเงิน
แสดง:
- เลขที่และวันที่จัดทำ
- ผู้จัดทำ/ผู้เบิก
- ผู้ขายหรือผู้รับเงินเท่าที่ทราบ
- วันที่เกิดค่าใช้จ่าย
- รายละเอียด วัตถุประสงค์ และยอดเงิน
- เหตุผลที่ไม่มีใบเสร็จ
- หลักฐานประกอบ
- ผู้จัดทำ ผู้ตรวจสอบ และผู้อนุมัติตาม workflow

อย่าบังคับเลขภาษีที่ไม่ทราบ และอย่าเปลี่ยนเอกสารนี้เป็นใบกำกับภาษี

### 4.9 ใบสำคัญจ่าย
แสดง:
- เลขที่ วันที่ และผู้รับเงิน
- รายการรายจ่ายหรือเอกสารที่นำมาจ่าย
- หมวดบัญชีตามระบบเดิม
- ยอดก่อนหัก ภาษีหัก ณ ที่จ่าย และยอดจ่ายสุทธิ
- วิธีชำระ บัญชีที่จ่าย และเลขอ้างอิง
- หลักฐานชำระเงิน
- ผู้จัดทำ ผู้ตรวจสอบ ผู้อนุมัติ และผู้รับเงินตามสิทธิ์

เชื่อมรายการต้นทางเพื่อป้องกันสร้างรายจ่ายซ้ำ

### 4.10 ใบกำกับภาษีอย่างย่อ
แสดง:
- ข้อมูลผู้ออกเอกสาร เลขที่ และวันที่
- รายการสินค้า/บริการ
- ยอดรวมและข้อมูลภาษีตามที่ปรากฏ
- ข้อมูลผู้ซื้อเป็นส่วนเพิ่มเติมตามเอกสารจริง

ใช้ validation แยกจากใบกำกับภาษีเต็มรูป ไม่บังคับทุกช่องเหมือนกัน

### 4.11 ใบเพิ่มหนี้ / ใบลดหนี้
ทำฟอร์มแยกตามประเภทโดยใช้โครงสร้างร่วม:
- เลขที่ วันที่ และคู่ค้า
- เอกสารต้นทาง
- เหตุผลการเพิ่มหนี้/ลดหนี้
- รายการที่ปรับ จำนวน และมูลค่า
- มูลค่าก่อนปรับ มูลค่าที่ปรับ และมูลค่าหลังปรับเมื่อคำนวณได้จากข้อมูลจริง
- ฐานภาษี VAT และยอดปรับรวม

กำหนดทิศทางการปรับให้ชัด ใช้ convention จำนวนเงินเดียวกับ backend ป้องกันกลับเครื่องหมายสองครั้ง และไม่ทับเอกสารต้นทาง

### 4.12 หนังสือรับรองการหักภาษี ณ ที่จ่าย
แสดง:
- เลขที่และวันที่ออก
- ผู้จ่ายเงิน/ผู้มีหน้าที่หัก
- ผู้รับเงิน/ผู้ถูกหัก
- ข้อมูลชื่อ ที่อยู่ และเลขภาษีของแต่ละฝ่าย
- ตารางประเภทเงินได้ วันที่จ่าย ยอดเงินได้ อัตรา และภาษีที่หัก
- ยอดเงินได้รวมและภาษีที่หักรวม
- เงื่อนไขการหักและข้อมูลเพิ่มเติมตาม model จริง
- เอกสารการจ่ายที่เกี่ยวข้อง
- ผู้ลงนามตาม workflow

รองรับหลายรายการเงินได้ และไม่สร้างรายจ่ายต้นทางซ้ำ

หากไม่มี template และกฎที่ตรวจสอบได้สำหรับแบบทางการ ให้รองรับการเก็บข้อมูลและแนบต้นฉบับก่อน ไม่อ้างว่าออกแบบทางการได้แล้ว

### 4.13 หลักฐานโอนเงิน / Slip
แสดง:
- วันและเวลาทำรายการ
- ผู้โอนและผู้รับ
- ธนาคารและบัญชีเท่าที่ปรากฏ
- จำนวนเงิน สกุลเงิน ค่าธรรมเนียมถ้ามี
- เลขอ้างอิงธุรกรรม
- รายการหรือเอกสารที่นำมาจับคู่
- ผลการจับคู่และยอดที่จัดสรร

ไม่แสดงตารางสินค้า VAT หรือวันครบกำหนดโดยไม่เกี่ยวข้อง

การมีภาพ Slip ไม่เท่ากับตรวจสอบกับธนาคารสำเร็จ

### 4.14 เอกสารธนาคารประเภทอื่น
แสดง:
- ประเภทเอกสารย่อย
- ธนาคาร บัญชี และวันที่
- เลขอ้างอิง
- รายละเอียดธุรกรรม
- จำนวนเงินที่เกี่ยวข้อง
- เอกสารหรือรายการต้นทาง

เลือก fields ตามประเภท เช่น ใบฝาก ใบถอน หรือรายการค่าธรรมเนียม ไม่ใช้ Statement แทนทุกประเภท

### 4.15 Statement
แสดง:
- ธนาคาร บัญชี เจ้าของบัญชี และสกุลเงิน
- ช่วงวันที่ ยอดยกมา และยอดปิด
- ตารางธุรกรรม: วันที่ รายละเอียด เลขอ้างอิง เงินเข้า เงินออก และยอดคงเหลือ
- สถานะจับคู่ของแต่ละรายการ

ใช้ workflow Statement เดิมถ้ามี รองรับตรวจและแก้รายแถว ไม่ยุบทั้งหมดเป็นยอดเงินช่องเดียว และไม่สร้างธุรกรรมซ้ำจากการนำเข้าเดิม

### 4.16 เอกสารอื่น / ยังไม่ทราบประเภท
แสดง:
- ชื่อหรือคำอธิบายเอกสาร
- เลขที่และวันที่ถ้าทราบ
- คู่ค้าที่เกี่ยวข้อง
- จำนวนเงินและสกุลเงินเป็นข้อมูลทางเลือก
- หมายเหตุและไฟล์ประกอบ

บันทึกร่างได้โดยไม่บังคับข้อมูลที่ไม่เกี่ยวข้อง และเปลี่ยนไปประเภทที่ถูกต้องภายหลังได้

## 5. พฤติกรรมฟอร์มที่ต้องเปลี่ยนจริง

เมื่อเลือกประเภท:
- เปลี่ยนชื่อหัวข้อ บทบาทคู่ค้า sections ตาราง และ validation ทันที
- ช่องที่ไม่เกี่ยวข้องต้องไม่ปรากฏเป็น required
- เก็บค่าของช่องที่ซ่อนใน state และ persistence ตาม model ที่เหมาะสม
- ไม่ใช้ค่าของช่องที่ซ่อนไปคำนวณยอดผิดประเภท
- เปลี่ยนกลับแล้วค่าที่กรอกยังอยู่

OCR เป็นคำแนะนำ ผู้ใช้แก้และเลือกประเภทเองได้

ค่าที่อ่านไม่พบต้องว่าง ไม่เติม 0 วันที่วันนี้ หรือชื่อคู่ค้าจำลอง

นำระบบยืนยันผล OCR ทีละช่องออกจาก workflow หลัก ใช้การยืนยันระดับเอกสารตามข้อกำหนดเดิม

ช่องที่ติด validation ต้องมีข้อความไทยและ focus ได้จริง

## 6. แบบพิมพ์และ PDF

สำหรับประเภทที่ออกเอกสารได้จริง:
- ออกแบบ template ให้ตรงข้อมูลและบทบาทของประเภทนั้น
- ใช้ข้อมูลธุรกิจ สาขา โลโก้ และคู่ค้าจริง
- ใช้เลขเอกสารจากระบบเดิม พร้อมป้องกันเลขซ้ำที่ backend
- แสดงสถานะร่างอย่างชัดเจน
- รองรับภาษาไทยและรูปแบบวันที่เดิม
- รองรับ A4 ตารางหลายหน้า หัวตารางซ้ำ และข้อความยาว
- จัดยอดรวม หมายเหตุ และพื้นที่ลงนามไม่ให้ทับกัน
- แยกยอดรวมเอกสาร ภาษีหัก ณ ที่จ่าย และยอดชำระให้ถูกความหมาย
- ไม่แสดงปุ่มหรือข้อมูล OCR ภายในเอกสารพิมพ์

หากมี PDF renderer เดิมให้ใช้ต่อ ไม่เพิ่มระบบใหม่โดยไม่จำเป็น

ถ้าเอกสารที่นำเข้าต้องพิมพ์สรุปข้อมูล ให้ระบุว่าเป็นสรุปข้อมูลจากระบบ ไม่ทำให้เข้าใจว่าเป็นต้นฉบับที่ออกโดยคู่ค้า

## 7. เชื่อมการบันทึกให้ครบ

ตรวจทั้ง frontend และ backend:
- field ที่เพิ่มต้องบันทึกและโหลดกลับได้
- partial update แยก field ที่ไม่ส่งจากการล้างค่า
- validation ตามประเภทและ action
- organization isolation และ permissions
- snapshot คู่ค้า
- decimal precision และ rounding
- เอกสารอ้างอิงและการป้องกันรายการซ้ำ
- audit และ concurrency ตามข้อกำหนดเดิม

ห้ามแก้เฉพาะหน้าตาแต่ส่ง payload เก่าที่ทำข้อมูลใหม่สูญหาย

หากต้องเพิ่ม schema ให้เตรียม migration ที่เข้ากันได้กับเอกสารเก่า ไม่รัน destructive migration หรือ deploy production โดยอัตโนมัติ

## 8. ลำดับทำงานและเกณฑ์ตรวจรับ

เริ่มจากใบเสร็จ ใบกำกับภาษี เอกสารรวม และใบแจ้งหนี้ ให้ครบวงจร render → edit → save → reopen ก่อน แล้วทำประเภทที่เหลือจนจบขอบเขต

อย่าหยุดหลังทำเพียงสี่ประเภทแรก

ตรวจอย่างน้อย:
1. เปิดฟอร์มจาก route ที่ผู้ใช้ใช้งานจริง
2. เลือกแต่ละประเภทแล้ว sections และบทบาทคู่ค้าเปลี่ยนจริง
3. กรอกข้อมูลเฉพาะประเภท บันทึก และเปิดใหม่แล้วข้อมูลครบ
4. เปลี่ยนประเภทไปกลับแล้วค่าที่กรอกไม่หาย
5. บันทึกร่างข้อมูลไม่ครบได้ แต่ยืนยันตรวจตามกติกาประเภทนั้น
6. ใบส่งของไม่ถูกบังคับยอดเงิน
7. Slip ไม่ถูกบังคับตารางสินค้าและ VAT
8. ใบวางบิลเลือกและรวมใบแจ้งหนี้หลายใบได้
9. Statement แสดงและจัดการธุรกรรมหลายแถวได้
10. ใบเพิ่มหนี้/ลดหนี้อ้างอิงต้นทางและไม่กลับเครื่องหมายซ้ำ
11. เอกสารพิมพ์ใช้ข้อมูลและยอดตรงกับข้อมูลที่บันทึก
12. Desktop และ mobile ใช้งานได้ ไม่มีช่องหรือปุ่มล้นจอ

เพิ่ม tests ตามความเสี่ยง รัน lint, typecheck, tests และ build ที่ repository มีจริง ตรวจ UI จริงหากเครื่องมือรองรับ

หากตรวจ UI ไม่ได้ ให้ระบุสิ่งที่ยังไม่ได้พิสูจน์ ห้ามรายงานว่าหน้าจอผ่านแล้วจากการอ่านโค้ดอย่างเดียว

## 9. เงื่อนไขการจบงาน

ห้ามถือว่างานเสร็จจากเพียง:
- เพิ่ม enum ประเภทเอกสาร
- เพิ่ม configuration ที่ยังไม่ได้เชื่อมกับ renderer
- สร้าง component ที่ route จริงไม่ได้ใช้
- เปลี่ยนชื่อหัวข้อแต่ช่องกรอกยังเหมือนเดิม
- ทำ mockup ที่บันทึกไม่ได้
- ปรับ backend แต่ฟอร์มเดิมยังแสดงอยู่

รายงานผลเป็นตาราง:
ประเภทเอกสาร | route/component ที่ใช้งาน | ฟอร์มที่เปลี่ยน | บันทึกและเปิดใหม่ | แบบพิมพ์/PDF | ผลตรวจจริง | ข้อจำกัด

ระบุไฟล์ที่แก้ คำสั่งตรวจที่รัน และผลจริง

ถ้ามีข้อจำกัดภายนอก ให้ทำส่วนที่ไม่ติดข้อจำกัดต่อ พร้อมระบุ dependency ที่ขาดและขั้นตอนแก้ไขอย่างเจาะจง ไม่ใช้ข้อจำกัดของเอกสารประเภทเดียวเป็นเหตุให้หยุดทั้งงาน

เริ่มตรวจ repository และแก้โค้ดจริงทันที ไม่ต้องตอบเพียงคำแนะนำหรือถามซ้ำว่าต้องการให้ลงมือหรือไม่
