# Phase 8 — Accounting Suggestion and Export Mapping decisions

Status: decisions approved for the gated Phase 8 implementation on 2026-09-23. These decisions do not authorize database migration, feature activation, or accounting posting. The first release uses a generic export only; destination-specific compatibility is deferred until a real workbook and import test exist.

## Agreed boundary

- Start with expense-side Documents only. One confirmed Phase 7 Document revision produces at most one Accounting Suggestion; a mixed-purpose Document needs human review rather than invented line-item splits.
- Expense Categories are flat, editable, and owned by one Organization. The Phase 3 reference-data design is the intended starting point, but its category tables are not assumed to be shipped.
- Vendor matching requires an unambiguous strong identity, including branch when relevant. Add an optional reviewed seller-branch field before relying on it; missing or conflicting identity does not trigger an automatic match. Name similarity alone is not a match.
- A Vendor-to-category rule offers a candidate, not an authoritative classification. Only an Owner/Admin may approve a reusable Organization rule; correcting one Document never creates one silently. Deterministic priority is an approved per-Document decision, then an approved exact Vendor + document-type rule, then an approved Vendor default, then no suggestion. Equal-priority conflicting rules leave the category unresolved; recency never breaks ties.
- The suggestion is tied to its confirmed source revision and carries the proposed Vendor/category, basis and rule version, warnings/status, and reviewer/time. Amounts come from confirmed extraction rather than a second unreviewed copy. No debit/credit posting, ledger account, tax treatment, or direct authoritative posting is in scope.
- Owner/Admin confirmation is required before exporting a suggestion. Members may propose corrections but cannot confirm or bulk export under the current role boundary. An Expense Category is required for Phase 8 approval; an unmatched Vendor may remain empty only with an explicit reason. Unknown optional values stay empty, never fabricated or represented as zero. A Document without an approved category can still use the separate Phase 7 structured export.
- Rule changes affect new suggestions only. A pending suggestion under an old rule version must be regenerated before approval. Source-review changes supersede derived suggestions; old exports remain versioned snapshots. Archived reference data cannot produce new matches, but old evidence remains explainable. Unmatched or conflicting suggestions appear in a review queue; a Task is created only on explicit assignment.
- No LLM fallback or external AI transmission in the initial scope. Show rule provenance and uncertainty states rather than uncalibrated percentages.
- Suggestion states are `Draft`, `NeedsReview`, `Approved`, `Superseded`, and `Failed`. Initial bounded warning codes include `vendor_unmatched`, `branch_unknown`, `category_unmatched`, `rule_conflict`, and `source_changed`. `Failed` is a technical failure, not a business ambiguity; Phase 6 OCR confidence is not suggestion confidence.
- Audit suggestion creation/review, rule changes, template selection/version, and export transitions with actor, Organization, IDs, versions, and time; do not put document content or Vendor names in operational logs.
- The first export is generic CSV/XLSX, one row per approved current Document revision, not a claimed import-ready file. It contains only reviewed source values, the approved Vendor/category (Vendor may be blank with reason), rule basis/version, warning codes, approval time, and a stable row identifier. Raw OCR text, invented account/tax/payment codes, and executable spreadsheet content are excluded. Empty means unknown and numeric `0.00` means an actual reviewed zero. Re-exporting the same approved revision preserves the row identifier, but PlaiFlow cannot guarantee deduplication after a user imports a file elsewhere.
- A future destination template is fixed, platform-owned, and versioned; each Organization owns only its mapping values, not arbitrary columns or spreadsheet formulas. A destination adapter requires its current official workbook and a verified trial import.
- Run deterministic rules before any future fallback. Cache stable lookups within the Organization and rule version only; measure unresolved/conflict rate, cache hit rate, latency P50/P95, and provider cost (zero while LLM is disabled) without content-bearing metric labels.

## Still open

- The first named destination and its official current import workbook remain unselected; destination compatibility is out of the first release.
- Exact generic export column names/order and the later destination adapter import-validation contract must be set in the Phase 8 specification; the semantic fields above are fixed.
- Numeric latency/cost acceptance targets require a measured baseline. Correction-history retention requires a legal/privacy decision before production; the existing export-artifact or audit defaults are not assumed sufficient. Phase 7 release prerequisite evidence also remains required.
